# Cross-language feature parity

This matrix tracks feature parity between libo11y implementations against
the project's reference capability set: the design distilled in
[DESIGN.md](DESIGN.md), which every language must satisfy in its native
idiom. Parity means the capability exists idiomatically, not that APIs are
identical. Capabilities that belong to application or organizational policy
rather than to a general-purpose library are listed at the bottom with the
generic mechanism libo11y provides instead.

Legend: full = implemented, idiom = implemented in a deliberately different,
language-native form, planned = not yet started, excluded = will not be
implemented (rationale given), gap = a known limitation of a runtime or of
upstream OpenTelemetry, with its issue.

The TypeScript columns describe the `@libo11y/*` packages on Bun 1.3.13 and
Node 24. They are built on OpenTelemetry JS 3.x (`@opentelemetry/api`
1.10.0, the SDK packages at 3.1.1 and the OTLP exporters at 0.301.1).

The Zig columns describe `libo11y-zig` (`zig/v0.1.0`) on Zig 0.17.1. Because
upstream `opentelemetry-zig` did not meet the contract (process-global
configuration, un-deadlined shutdown and retries, unredacted exemplars,
missing TLS client certs/ALPN), libo11y Zig owns its telemetry pipeline
over vendored `opentelemetry-proto` bindings (`zig-protobuf`) and `tls.zig`.

The C columns describe `libo11y` C (`c/`, unreleased, targeting `c/v0.1.0`),
a pure ISO C11 public ABI (`o11y/o11y.h`, `o11y/spec.h`, `o11y/test.h`,
C++ `extern "C"` safe) backed by libo11y's Zig telemetry engine with zero
external runtime dependencies beyond libc and pthreads.

The matrix describes the latest releases: `go/v0.3.0`, `ts/v0.2.0`, and
`zig/v0.1.0`, plus the unreleased C11 implementation in `c/`.

A status describes how a capability is designed and built. It does not say
the release is free of defects in it. The section "Known defects in the
current releases" lists those.

## TypeScript-only rows

These rows have no Go counterpart, or they record why the TypeScript form
differs.

| Capability | TS status | TS form and reason |
|---|---|---|
| Exemplars built by libo11y | idiom | `@opentelemetry/sdk-metrics` 3.1.1 records no exemplars, and `otlp-transformer` serializes none ([open-telemetry/opentelemetry-js#5147](https://github.com/open-telemetry/opentelemetry-js/issues/5147)). The core's meter-provider wrapper samples them, and libo11y's serializers write them over upstream's OTLP transport, which keeps retries, compression and headers. libo11y will switch to upstream exemplars behind the same API once they ship |
| OTLP over HTTP only | idiom | `http/protobuf` (default) and `http/json`. `grpc` for any signal exported over OTLP fails `setup` and `createTelemetry` with `UNSUPPORTED_PROTOCOL`, because gRPC under Bun is unverified and would add `@grpc/grpc-js`. gRPC can come later in a minor release |
| The recorder's context manager | idiom | OpenTelemetry JS keeps one context manager per process. When none is registered, `createRecorder` installs an `AsyncLocalStorageContextManager` and removes it when the last recorder shuts down. It is the only global the harness touches. Go passes context explicitly, so `o11ytest` needs none |
| Bun 1.3.13 context gaps | gap | the `AsyncLocalStorage` context is lost in an async generator used as a `Bun.serve` body ([oven-sh/bun#24199](https://github.com/oven-sh/bun/issues/24199)), in a thenable returned after an `await` ([oven-sh/bun#34266](https://github.com/oven-sh/bun/issues/34266)) and in `unhandledRejection` listeners ([oven-sh/bun#40223](https://github.com/oven-sh/bun/issues/40223)). `instrumentServe` ends its spans correctly regardless. Tests mark each gap and fail when Bun fixes it |
| Exemplars go to the first reader | gap | the exemplar store hands each sample to the first reader that collects, so with several metric readers the others get no exemplars for it |
| Export timeout default of 5 s | idiom | `OTEL_BSP_EXPORT_TIMEOUT`, `OTEL_BLRP_EXPORT_TIMEOUT` and `OTEL_METRIC_EXPORT_TIMEOUT` default to 5000 ms, where sdk-node uses 30000 ms. Upstream's batch processors and periodic reader arm an export timer that keeps the process alive, so a hung exporter would hold an exiting process for the full timeout even after shutdown resolved. 5000 ms matches the shutdown deadline. An explicit variable still wins. A connection attempt that is still pending when shutdown resolves holds the process longer on both runtimes (see the known defects) |
| `logProcessor` | idiom | the counterpart of Go's `WithExtraLogHandler`. It is a log record processor after the redacting processor and before the batch processor, so it sees each classified record synchronously in `onEmit` |
| Unclassified record body | gap | the policy classifies attributes by key, never a log record's body. Go has the same gap |
| No environment-resource shadowing | idiom | the JS providers do not merge the environment resource themselves, so a key the policy drops from `OTEL_RESOURCE_ATTRIBUTES` cannot return. Go shadows such keys with empty values because its SDK reads the environment again. A test proves a PII key from the environment is absent from exported spans |
| Kubernetes identity through `OTEL_RESOURCE_ATTRIBUTES` | idiom | the server platform has no Downward API detector. A detector would need environment variable names of its own, and libo11y reads only `OTEL_*`. Go has no detector either. The server README has the manifest snippet |

## Known defects in the current releases

These are places where a release breaks a rule of the design contract. Each
one is a defect to fix, not a decision. Every one is fixed on `main`, and
each library's changelog describes the fix under Unreleased. The fixes
reach users with the next release of each library.

| Release | Defect | Rule it breaks |
|---|---|---|
| `ts/v0.2.0` | the application registry's reserved list misses the semconv root `state` | reserve the root of every semconv attribute |
| `ts/v0.2.0` | `OTEL_PROPAGATORS` is not read, so a process that sets it keeps the W3C default | standard `OTEL_*` variables are honored |
| `ts/v0.2.0` | a PII token for an array of more than 2047 elements differs between a log record and a span or resource attribute, because only the log path bounds the rendering | one canonical rendering shared by every signal |
| `ts/v0.2.0` | logger methods rethrow an exception from a user `attrReplacer` or from an attribute that cannot be read, wide-record and instrument calls throw on an unreadable attribute too, and `instrumentFetch` and `instrumentServe` let a failing user propagator fail the request | never be the reason the host fails |
| `ts/v0.2.0` | an option value outside its allowed set is accepted silently. An unknown `logLevel` drops every record | initialization fails fast on configuration errors |
| `ts/v0.2.0` | a `piiHashKey` given as a string, which JavaScript allows and the type forbids, is converted to an empty byte array, so every token is HMAC-SHA256 under an empty key. A `Uint8Array` key is not affected | hash mode requires a key of at least 32 bytes |
| `ts/v0.2.0` | a `forceFlush` that overlaps another can resolve as ok before its caller's own log records have been exported | never drop buffered telemetry without saying so |
| `ts/v0.2.0` | a final log or metric export that the collector rejects reaches the error handler but not the shutdown report, which can say `ok: true`. A rejected trace export is in the report | shutdown reports per-signal failures |
| `ts/v0.2.0` | a connection attempt still pending when shutdown resolves keeps the process alive past the deadline: until the exporter's request timeout on Bun (10 s by default), and until the operating system gives up on Node (about 135 s on Linux) | bounded shutdown |
| `ts/v0.2.0` | `shutdownOnSignals` gives `beforeShutdown` and `shutdown` a full deadline each, so it can take twice the stated bound | bounded shutdown |

## Upcoming and planned clients

No released implementation exists yet for Rust, Python, or Java. When each
ships, it gets its own status and form columns in the matrix above, against
the same baseline.

- **Rust** (coming soon): under active development in `rust/` on
  `tracing` and OpenTelemetry Rust. `libo11y-spec`, `libo11y-redact` (with
  the `Redact` derive macro), and the core identity, policy, and
  application-registry crate are on `main`; traces, logs, metrics,
  `libo11y-test`, and HTTP, RPC, and database integrations are in progress.

  OpenTelemetry Python SDK 1.45, targeting a single `libo11y` PyPI
  distribution with optional extras, stdlib `logging`, `@redacted`
  capture-time redaction, and native ASGI, WSGI, httpx, requests, gRPC,
  Connect, and DB-API integrations.
- **Java** (planned): not started; planned to build over the OpenTelemetry
  Java SDK and SLF4J.
