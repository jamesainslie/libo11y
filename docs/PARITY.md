# Cross-language feature parity

This matrix tracks feature parity between libo11y implementations against
the project's reference capability set: the design distilled in
[DESIGN.md](DESIGN.md), which every language must satisfy in its native
idiom. Parity means the capability exists idiomatically, not that APIs are
identical. Capabilities that belong to application or organizational policy
rather than to a general-purpose library are listed at the bottom with the
generic mechanism libo11y provides instead.

Legend: full = implemented, idiom = implemented in a deliberately different,
language-native form, planned = not yet started, excluded = will not be
implemented (rationale given), gap = a known limitation of a runtime or of
upstream OpenTelemetry, with its issue.

The TypeScript columns describe the `@libo11y/*` packages on Bun 1.3.13 and
Node 24. They are built on OpenTelemetry JS 3.x (`@opentelemetry/api`
1.10.0, the SDK packages at 3.1.1 and the OTLP exporters at 0.301.1).

The Zig columns describe `libo11y-zig` (`zig/v0.1.0`) on Zig 0.17.1. Because
upstream `opentelemetry-zig` did not meet the contract (process-global
configuration, un-deadlined shutdown and retries, unredacted exemplars,
missing TLS client certs/ALPN), libo11y Zig owns its telemetry pipeline
over vendored `opentelemetry-proto` bindings (`zig-protobuf`) and `tls.zig`.

The Python columns describe `libo11y` (`python/v0.1.0`) on CPython 3.12,
3.13, and 3.14. It is built on OpenTelemetry Python SDK 1.45
(`opentelemetry-sdk==1.45.*`), shipping one PyPI distribution with optional
extras for third-party integrations and isolating the private
`opentelemetry.sdk._logs` module behind `libo11y._internal.logs_bridge`.

The C columns describe `libo11y-c` (`c/v0.1.0`),
a pure ISO C11 public ABI (`o11y/o11y.h`, `o11y/spec.h`, `o11y/test.h`,
C++ `extern "C"` safe) backed by libo11y's Zig telemetry engine with zero
external runtime dependencies beyond libc and pthreads.

The Rust columns describe the eleven-crate `rust/` workspace (`rust/v0.1.0`:
`libo11y`, `libo11y-spec`, `libo11y-redact`, `libo11y-macros`, `libo11y-test`,
`libo11y-http`, `libo11y-reqwest`, `libo11y-tonic`, `libo11y-connect`,
`libo11y-sqlx`, and `libo11y-cli`), built on Rust edition 2024 (workspace MSRV
1.88; `libo11y-sqlx` requires 1.94), `tracing` 0.1.44, and OpenTelemetry Rust
0.33.1.

The matrix describes the latest releases: `go/v0.3.0`, `ts/v0.2.1`,
`zig/v0.1.0`, `python/v0.1.0`, `c/v0.1.0`, and `rust/v0.1.0`.

A status describes how a capability is designed and built. It does not say
the release is free of defects in it. The section "Known defects in the
current releases" lists those.

| Exemplars go to the first reader | gap | the exemplar store hands each sample to the first reader that collects, so with several metric readers the others get no exemplars for it |
| Export timeout default of 5 s | idiom | `OTEL_BSP_EXPORT_TIMEOUT`, `OTEL_BLRP_EXPORT_TIMEOUT` and `OTEL_METRIC_EXPORT_TIMEOUT` default to 5000 ms, where sdk-node uses 30000 ms. An explicit variable still wins. Shutdown ends the requests in flight when its deadline passes. | No environment-resource shadowing | idiom | the JS providers do not merge the environment resource themselves, so a key the policy drops from `OTEL_RESOURCE_ATTRIBUTES` cannot return.
