# libo11y conventions

## Repository layout

```
libo11y/
  docs/          cross-language design contract, spec, and conventions
  spec/          telemetry specification registry: the shared,
                 language-neutral source of truth
  go/            Go modules (github.com/jamesainslie/libo11y/go and the
                 o11ygin, o11yconnect, and o11ysql submodules), and
                 go/o11yrum, the RUM gateway module on its own version
                 line
  ts/            TypeScript workspace: Bun, the @libo11y/* packages
  conformance/   shared cases and vectors every implementation must
                 reproduce exactly
  scripts/       release and schema checks, with their tests
  rust/          Rust workspace (in development)
  java/          Java/Maven module (planned)
  zig/           Zig package (zig/v0.1.0), published through the
                 root build.zig and build.zig.zon shim
  python/        Python package (python/v0.1.0), published to PyPI as
                 libo11y with optional extras
  c/             C11 library (pure C11 ABI backed by zig/)
```

Each language directory is self-contained: its own build, tests, lint
configuration, changelog, and README. The `spec/` registry is the shared,
language-neutral source of truth; each language generates typed constants
and validation tables from it.

## Specification toolchain

The specification is validated and generated by the repository's own Go
tool (`go/internal/specgen`); the toolchain needs nothing beyond the Go
module itself. Make targets from the repository root:

- `make spec-check` decodes every registry group file strictly (the
  manifest is the one file decoded leniently) and validates the registry
  against the libo11y policy suite: naming, namespace ownership, sensitivity and
  cardinality classification, references and tombstones, enums, event
  discipline, and metric naming/unit rules. Rule IDs are listed in
  [SPEC.md](SPEC.md), section 8.
- `make spec-generate` validates first, then regenerates `go/spec`,
  `go/internal/spectables`, `docs/taxonomy`,
  `ts/packages/spec/src/generated`, `rust/libo11y-spec/src/generated`,
  `zig/src/spec/generated`, `python/src/libo11y/spec/_generated`,
  `c/include/o11y/spec.h`, and the OpenTelemetry schema files under
  `spec/schemas` from the registry. An invalid registry
  generates nothing. Generated files are never edited by hand.
- `make spec-drift` fails if generated artifacts are stale or if the
  generator produced files git does not track. CI runs it, and a golden
  test in `go test` catches stale generated files too. Only `spec-drift`
  catches the untracked ones.

The upstream semantic-conventions release the registry extends is pinned
as `semconv_version` in `spec/registry/manifest.yaml`; referenced upstream
attributes are defined by that release and never redefined here.

## TypeScript toolchain

The TypeScript workspace in `ts/` pins its toolchain exactly. It uses
`bun@1.3.13` as the package manager, `typescript@7.0.2`,
`@biomejs/biome@2.6.8` for linting and formatting,
`@microsoft/api-extractor@7.60.1` for the API reports, and
`@types/bun@1.4.4` and `@types/node@24.19.2` for runtime types. CI runs
every suite on Bun 1.3.13 and Node 24.

- **Tests.** Tests use `node:test` and `node:assert/strict`, never
  `bun:test`, so one suite runs under both runtimes: `bun run test:bun`
  runs `bun test`, and `bun run test:node` runs `node --test`. Imports use
  `.ts` specifiers. Node runs the sources through type stripping, so
  source files use only erasable syntax (`erasableSyntaxOnly`).
- **Build.** `bun run build` removes each package's `dist/`, then runs
  `tsc` and writes ESM JavaScript and declarations there. tsc rewrites the `.ts`
  specifiers to `.js` in the JavaScript. Exported functions declare their
  return types (`isolatedDeclarations`).
- **API reports.** Each package commits its public API as
  `api/<name>.api.md`, one report per entry point. `bun run api:check`
  fails when a build's API differs from the committed report. After a
  deliberate API change, run `bun run build && bun run api` and commit the
  updated report.
- **Size budgets.** `ts/size-budget.json` budgets the browser bundles in
  bytes of minified, gzip-compressed output. Each entry is an ES module
  source that imports from `@libo11y/*`, measured on its own. Each delta
  is measured against a base entry, so it is what one RUM collector adds.
  `bun scripts/size.ts --check` (`make ts-size`) fails when a bundle is
  over its budget. A package or collector that ships browser code adds
  its entry or delta in the same change. A budget increase is a reviewed
  diff of the file, with the measured number in the commit message.
- **Overhead benchmark.** `bun run bench:browser` (in `ts/`) measures the
  extra main-thread task time `@libo11y/rum` adds per soft navigation and
  per click in Chromium, through the DevTools protocol's `TaskDuration`,
  as the median of five runs with and without RUM. It writes
  `ts/dist/bench/overhead.json`, and `bun scripts/overhead-report.ts` turns
  that into a table and fails above `--max-view-ms` and
  `--max-interaction-ms`. The `ts-bench` workflow runs both on pushes to
  `main` and on pull requests that touch `ts/`, puts the table in the job
  summary and uploads the JSON as the `rum-overhead` artifact. The limits
  (8 ms per view, 4 ms per interaction) guard against regressions and are
  not a target. It is a benchmark: never run it on a shared machine
  without the owner's approval. CI runs it; elsewhere it skips itself
  unless `LIBO11Y_BENCH=1` is set.
- **Packing.** `ts/scripts/release.ts` sets the lockstep version
  (`version X.Y.Z`) and packs each package (`pack OUTDIR`). The packed
  `package.json` has exact versions in place of `workspace:` ranges, and
  its `exports` and `bin` point at `dist/`. `pack` refuses a `dist/` file
  with no matching source in `src/`.

`make ts-check` installs the locked dependencies, then lints, typechecks,
builds, checks the API reports, and runs every suite under Bun and Node.
`make ci` runs it.

## Zig toolchain

The Zig package in `zig/` (re-exported through the root `build.zig` and
`build.zig.zon` shim) pins Zig `0.17.1`. On NixOS development machines it
comes from home-manager with `mitchellh/zig-overlay` (`mise` does not manage
Zig). CI installs it with `mlugg/setup-zig` pinned by commit and runs
`make zig-check` on Linux and macOS, plus `make zig-integrations-check` on
Linux with a PostgreSQL 17 service container.

- **Formatting.** `zig fmt --check` runs over `build.zig`, `build.zig.zon`,
  and `zig/` (excluding `.zig-cache`, `zig-pkg`, and `zig-out`).
- **Tests.** `make zig-check` runs `zig build test` through the root shim in
  both `Debug` and `ReleaseSafe` with `-j$(ZIG_BUILD_J)` (default 8). Every
  test uses `std.testing.allocator` so leaks fail the suite. The suite
  includes the shared conformance tests reading `conformance/` via
  `-Dconformance-dir`.
- **Optional integrations.** `o11yhttpz`, `o11ypg`, and `o11ysqlite` depend
  on lazy third-party packages (`http.zig`, `pg.zig`, `zig-sqlite`) gated
  behind `-Dhttpz=true`, `-Dpg=true`, and `-Dsqlite=true`.
  `make zig-integrations-check` enables all three in `Debug` and
  `ReleaseSafe`; set `O11YPG_TEST_DSN` to exercise live PostgreSQL queries.
- **Hygiene gate.** `scripts/zig-hygiene.sh` (tested by
  `make zig-hygiene-test`) rejects `@panic`, `std.debug.panic`,
  `std.debug.print` (including through aliases), and `catch`/`orelse
  unreachable` outside test blocks and test-only files (`zig/test/` and
  `*_test.zig`). Every switch on an error set returned by the public API is
  exhaustive.
- **Prose and commits.** Never use the em dash character anywhere in Zig
  sources, docs, or commit messages. Commits use `zig: <type>: <description>`
  and release tags use `zig/vX.Y.Z`.

## C toolchain

The C11 library in `c/` exposes a pure ISO C11 public ABI (`o11y/o11y.h`,
`o11y/spec.h`, `o11y/test.h`, C++ `extern "C"` safe) backed by `zig/` and
built with Zig `0.17.1`. Consumers linking the built `libo11y.a` / `libo11y.so`
(or `libo11ytest.a` in tests) need only a C11 compiler (`gcc`, `clang`) and
POSIX libc (`-lpthread -lm` on Linux).

- **Packaging.** `cd c && zig build -Doptimize=ReleaseSafe` installs static
  and shared libraries (`libo11y.a` with bundled compiler-rt, `libo11y.so`/`.dylib`),
  the self-contained test archive (`libo11ytest.a`), the `libo11y registry check`
  CLI (`bin/libo11y`), headers under `include/o11y/`, `lib/pkgconfig/libo11y.pc`,
  and `lib/cmake/libo11y/libo11yConfig.cmake`.
- **Tests and gates.** `make c-check` runs `zig fmt --check` over `c/build.zig`,
  `c/build.zig.zon`, and `c/src`, runs `scripts/zig-hygiene.sh c/build.zig c/src`,
  builds and executes all C11 unit, shared `conformance/`, OTLP HTTP/gRPC wire,
  and quickstart suites in both `Debug` and `ReleaseSafe`, runs `c/tests/test_cli.sh`,
  and links a standalone C11 program against `libo11y.a` with
  `cc -std=c11 -Wall -Wextra -Werror -Wpedantic`. CI runs `make c-check` in
  the `c` job on Linux and macOS.
- **Commits and releases.** Commits use `c: <type>: <description>` and release
  tags use `c/vX.Y.Z`.

## Python toolchain

The Python package in `python/` targets CPython 3.12, 3.13, and 3.14 on
`opentelemetry-sdk==1.45.*` and uses `uv` with a committed `python/uv.lock`.
CI installs `uv` with `astral-sh/setup-uv` pinned by commit and runs
`make python-check` on Linux and macOS across Python 3.12, 3.13, and 3.14,
plus a `python-integrations` job on Linux against a PostgreSQL 17 service
container (`O11Y_PG_TEST_DSN`).

- **Formatting and linting.** `ruff format --check src tests` and
  `ruff check src tests` enforce formatting and lint rules with zero
  warnings.
- **Type checking.** `pyright` runs in strict mode (`typeCheckingMode =
  "strict"`) over `src` and `tests`, and the package ships a PEP 561
  `py.typed` marker.
- **Tests.** `pytest -n $(PYTHON_WORKERS) --cov=libo11y --cov-branch` runs
  unit, shared `conformance/`, OTLP HTTP/gRPC wire, integration, and
  Hypothesis property suites in parallel (`PYTHON_WORKERS` caps xdist
  workers to a quarter of the machine's cores).
- **Hygiene gate.** `scripts/python-hygiene.sh` (tested by
  `make python-hygiene-test`) rejects `print(...)`, `builtins.print(...)`,
  `breakpoint()`, bare `except:`, and `except BaseException:` outside tests.
- **Prose and commits.** Never use the em dash character anywhere in Python
  sources, docs, or commit messages. Commits use
  `python: <type>: <description>` and release tags use `python/vX.Y.Z`.

## Versioning and releases

- Independent per-language versioning, path-prefixed tags: `go/v0.1.0`,
  `ts/v0.1.1`, `zig/v0.1.0`, `python/v0.1.0`, `c/v0.1.0`, `rust/v0.1.0`.
  The o11yrum gateway module has its own line: `go/o11yrum/v0.1.0`.
- Semantic versioning per language ecosystem norms.
- No lockstep releases across languages. A change to shared docs never
  forces a release.
- Each language keeps a `CHANGELOG.md` in Keep a Changelog format.
- The Go family is four modules: `github.com/jamesainslie/libo11y/go` and
  the submodules `go/o11ygin`, `go/o11yconnect` and `go/o11ysql`. They
  release together at one version. A release tags `go/vX.Y.Z` first, then
  `go/o11ygin/vX.Y.Z`, `go/o11yconnect/vX.Y.Z` and `go/o11ysql/vX.Y.Z`, all
  on the same commit, and each submodule's `go.mod` requires the parent at
  that version. `make release-check` validates the sequence for
  `RELEASE_VERSION` (default `v0.4.0`) against a throwaway local remote;
  it never touches real refs. The default always matches the version the
  submodules require, so it moves only in a release commit.
- To release Go version X.Y.Z: move the changelog's entries into a
  `## [X.Y.Z] - date` section, set each submodule's requirement on the
  parent module to `vX.Y.Z`, set `RELEASE_VERSION` in the `Makefile` and
  the default in `scripts/release-check.sh` to `vX.Y.Z`, and run
  `make release-check` on the commit to release. Then push the tags, all
  on that commit, in two pushes: `go/vX.Y.Z` on its own, then the three
  submodule tags. Never push all four together, because GitHub creates no
  push events when more than three tags are pushed at once. Each tag
  starts the release workflow (`.github/workflows/release.yml`). It
  checks that the version is
  semantic, that a submodule tag's parent tag exists on the same commit
  and matches its `go.mod` requirement, and that the changelog has the
  section, then runs vet, the tests, and the spec gates. It publishes a
  GitHub Release whose notes are that changelog section
  (`scripts/release-notes.sh`, reading `go/CHANGELOG.md`, which covers all
  four modules), marked as a prerelease only for versions with a
  `-prerelease` suffix, and requests the version from `proxy.golang.org`
  and builds a consumer against it.
- `go/o11yrum`, the RUM gateway module with its `o11yrum-gateway` command
  and container image, versions independently of the four lockstep Go
  modules. Its `go.mod` requires the parent at any released version and
  has no `replace` directive, because `go install` of the command at a
  tag refuses one. The `go.work` workspace resolves the parent from the
  checkout during development, and builds with `GOWORK=off`, such as
  `make tidy-check` and the image, use the required release. o11yrum
  therefore builds only against parent APIs that are already released.
  Its tag goes on any commit, on its own.
  `O11YRUM_RELEASE_VERSION` in the `Makefile` and the default in
  `scripts/o11yrum-release-check.sh` name the version being released and
  move only in a release commit.
- To release o11yrum version X.Y.Z:
  1. Move the entries under `## [Unreleased]` in `go/o11yrum/CHANGELOG.md`
     into a `## [X.Y.Z] - date` section, and update the link references
     at the end of the file.
  2. Make sure `go/o11yrum/go.mod` requires the parent at a version that
     has a `go/vA.B.C` tag. Raise it only when o11yrum needs something
     newer.
  3. Set `O11YRUM_RELEASE_VERSION` in the `Makefile` and the default in
     `scripts/o11yrum-release-check.sh` to `vX.Y.Z`.
  4. Run `git fetch --tags origin`, because the check looks for the
     parent's `go/` tag locally. Then run `make o11yrum-release-check` (or
     `make release-check`) and
     `make o11yrum-image` on the committed tree, then merge the release
     PR.
  5. Tag the merge commit and push the tag on its own:
     `git tag go/o11yrum/vX.Y.Z <merge-sha> && git push origin
     go/o11yrum/vX.Y.Z`.

  The release workflow checks that the version is semantic, that the
  parent version `go.mod` requires has a `go/` tag, that
  `O11YRUM_RELEASE_VERSION` matches the tag, and that the changelog has
  the section. It runs vet, the tests, the spec gates and
  `scripts/o11yrum-release-check.sh`. It then publishes the GitHub Release
  from `go/o11yrum/CHANGELOG.md`, never marked Latest, because the main Go
  module keeps Latest. It requests the version from `proxy.golang.org`
  and builds a consumer against it. The `image` job builds
  `ghcr.io/jamesainslie/o11yrum-gateway` for `linux/amd64` and
  `linux/arm64`, and pushes it tagged `X.Y.Z`, and also `X.Y` and
  `latest` for a version without a `-prerelease` suffix. It attests the
  build provenance with `actions/attest-build-provenance`, smoke-tests the
  pushed image, and prints the digest in the job summary. Verify an image
  with `gh attestation verify
  oci://ghcr.io/jamesainslie/o11yrum-gateway:X.Y.Z --repo
  jamesainslie/libo11y`. GHCR creates a new package as private. The owner
  sets its visibility once, in the package settings on GitHub.
- TypeScript releases are lockstep. Every `@libo11y/*` package publishes
  at one shared version from a `ts/vX.Y.Z` tag. The first version on npm
  is 0.1.1. The `ts/v0.1.0` release never reached npm, because npm asked
  for 2FA on a direct publish from CI. The `ts/v0.2.0` release never
  reached npm either, because the trusted publishers allowed only staged
  publishing, so `@libo11y/web` and `@libo11y/webext` first appear at
  0.2.1. Every package keeps
  `"private": true` in the source tree, and `release.ts pack` drops it
  from each packed `package.json`, so only packed tarballs publish.
  `make release-check` also runs `scripts/ts-release-check.sh` for
  `TS_RELEASE_VERSION`. It checks every package is at that version, builds and packs
  the packages, checks each tarball's `exports` and `bin` targets, and
  installs the tarballs into a throwaway consumer that imports the server
  packages under Node and Bun and runs the `libo11y` and
  `libo11y-sourcemaps` bins. The consumer
  then bundles every entry point of `@libo11y/web`, `@libo11y/webext`
  and `@libo11y/rum` with `bun build --target=browser` through
  `scripts/ts-browser-bundle-check.sh`, which fails when the module graph
  holds a Node builtin or a Bun polyfill for one. Like `RELEASE_VERSION`,
  `TS_RELEASE_VERSION` moves only in a release commit, together with the
  package versions.
- To release TypeScript version X.Y.Z:
  1. Run `bun ts/scripts/release.ts version X.Y.Z`, which sets the
     version in every package.
  2. Move the `ts/CHANGELOG.md` entries into a `## [X.Y.Z] - date`
     section and update the link references.
  3. Set `TS_RELEASE_VERSION` in the `Makefile` and the default in
     `scripts/ts-release-check.sh` to `vX.Y.Z`.
  4. Run `make release-check` on the release commit, then merge it.
  5. Tag `ts/vX.Y.Z` on the merge commit and push that tag on its own.
  6. The release workflow verifies the tag, publishes every package that
     npm already has with provenance, installs the packages and creates
     the GitHub Release with every packed tarball attached. Nobody
     approves anything on npmjs.com.
- The release workflow routes each tag with `scripts/release-tag.sh`. For
  a `ts/` tag it checks that the version is semantic, that every
  `ts/packages/*/package.json` is at the tag's version, and that
  `ts/CHANGELOG.md` has the section. Then it runs `make ts-check` on Bun
  1.3.13 and Node 24 and packs and installs the tarballs with
  `scripts/ts-release-check.sh`. The publish job packs the packages again
  and runs `scripts/ts-npm-plan.sh plan`, which asks the registry about
  each package with `npm view`. A package that npm has publishes in
  dependency order with `npm publish --provenance` from a pinned npm
  11.21.2. A version the registry already has is skipped. A package that
  npm does not have yet is not published, and the job prints a warning
  naming it and lists it in the job summary. When a package on npm
  depends on a package new to npm through `dependencies`,
  `peerDependencies` or `optionalDependencies`, the plan fails the
  release before anything publishes, because npm consumers of that
  package would get a broken install. A prerelease version publishes
  under the `next` dist-tag. A smoke job waits up to ten minutes for the
  registry to serve the new version of every published package. It
  installs `@libo11y/server` and `@libo11y/test` into fresh projects
  under Node and Bun, and runs the `libo11y` and `libo11y-sourcemaps`
  bins under Node. It installs
  `@libo11y/web`, `@libo11y/webext` and `@libo11y/rum` into another fresh project and
  runs the same bundle check on them. In each of these installs, a
  package not on npm yet comes from its packed tarball. A last step
  installs every package not on npm yet from its tarball, with its other
  dependencies from the registry, and runs `scripts/ts-npm-plan.sh
  check`. The check fails on an incomplete dependency tree or on an entry
  point that does not resolve to a file under Node. Only after the smoke
  job passes is the GitHub Release created. The release is titled
  `@libo11y vX.Y.Z`, takes its notes from `ts/CHANGELOG.md`, and is never
  marked Latest, so the Go main module keeps Latest. It attaches every
  packed tarball. When a package is not on npm yet, the notes end with a
  paragraph that names it and gives its install command, such as `npm
  install
  https://github.com/jamesainslie/libo11y/releases/download/ts/vX.Y.Z/libo11y-rum-X.Y.Z.tgz`.
  That is the asset URL GitHub reports, and the same asset also serves
  with the slash in the tag encoded as `ts%2FvX.Y.Z`. `make
  ts-npm-plan-test` tests the plan script against fixture tarballs and a
  fake npm. Publishing authenticates with npm trusted publishing (OIDC),
  so the repository stores no npm token. Each package on npmjs.com trusts
  `release.yml` in `jamesainslie/libo11y`, with no environment, and
  allows `npm publish`. A tag ruleset lets only repository admins create,
  move or delete `ts/v*` tags, because pushing one publishes to npm.
- npm sets up trust only on a package that already exists, so trusted
  publishing cannot publish the first version of a new package. A
  release with a package new to npm completes without it, and consumers
  install that package from the tarball on the GitHub Release. To bring
  the package onto npm, a maintainer publishes the release's tarball with
  their own npm login (`npm publish --access public <file>.tgz`) and then
  sets up its trusted publisher the same way as the other packages. The
  next release publishes it like any other package. A package already on
  npm can depend on a new package only after the new package reaches npm
  this way. Until then the release fails at the plan step.
- Zig releases tag `zig/vX.Y.Z` on the release commit. Both manifests
  (`build.zig.zon` and `zig/build.zig.zon`) and `ZIG_RELEASE_VERSION` in the
  `Makefile` move together only in a release commit. To release Zig version
  `X.Y.Z`:
  1. Move `zig/CHANGELOG.md` entries into a `## [X.Y.Z] - date` section and
     update the link references.
  2. Set `.version = "X.Y.Z"` in `build.zig.zon` and `zig/build.zig.zon`,
     and set `ZIG_RELEASE_VERSION` in the `Makefile` and the default in
     `scripts/zig-release-check.sh` to `X.Y.Z` / `vX.Y.Z`.
  3. Run `make zig-check`, `make zig-integrations-check`, and (on the
     committed tree) `make release-check` or `make zig-release-check`, then
     merge the release PR.
  4. Tag `zig/vX.Y.Z` on the merge commit and push that tag.
  5. The release workflow (`scripts/release-tag.sh` routing `kind=zig`,
     `module=libo11y-zig`) checks both manifests and `zig/CHANGELOG.md`,
     runs `make zig-check` and `scripts/zig-release-check.sh`, publishes the
     GitHub Release titled `libo11y-zig vX.Y.Z` (never marked Latest, so Go
     keeps Latest), and runs a live `zig-smoke` job fetching
     `git+https://github.com/jamesainslie/libo11y#zig/vX.Y.Z` into a fresh
     consumer against an in-process OTLP receiver.
- Python releases publish one PyPI distribution (`libo11y`, with optional
  extras) from a `python/vX.Y.Z` tag. `python/pyproject.toml`,
  `python/uv.lock`, `PYTHON_RELEASE_VERSION` in the `Makefile`, and the
  default in `scripts/python-release-check.sh` move together only in a
  release commit. To release Python version `X.Y.Z`:
  1. Move `python/CHANGELOG.md` entries into a `## [X.Y.Z] - date` section
     and update the link references.
  2. Set `version = "X.Y.Z"` in `python/pyproject.toml`, run `cd python &&
     uv lock`, and set `PYTHON_RELEASE_VERSION` in the `Makefile` and the
     default in `scripts/python-release-check.sh` to `vX.Y.Z`.
  3. Run `make python-check` and `make release-check` (or
     `make python-release-check`), then merge the release PR.
  4. Tag `python/vX.Y.Z` on the merge commit and push that tag.
  5. The release workflow (`scripts/release-tag.sh` routing `kind=python`,
     `module=libo11y`) checks `python/pyproject.toml` and
     `python/CHANGELOG.md`, runs `make python-check` and
     `scripts/python-release-check.sh`, builds sdist and wheel with `uv
     build`, publishes to PyPI with `pypa/gh-action-pypi-publish@release/v1`
     using OIDC trusted publishing and PEP 740 attestations (no PyPI token
     stored in the repository), runs a `pypi-smoke` job installing
     `libo11y==X.Y.Z` from PyPI into a fresh venv against an in-process
     OTLP/HTTP receiver, and creates the GitHub Release titled
     `libo11y-python vX.Y.Z` (never marked Latest, so Go keeps Latest).
- C releases tag `c/vX.Y.Z` on the release commit. `c/build.zig.zon`,
  `C_RELEASE_VERSION` in the `Makefile`, and the default in
  `scripts/c-release-check.sh` move together only in a release commit. To
  release C version `X.Y.Z`:
  1. Move `c/CHANGELOG.md` entries into a `## [X.Y.Z] - date` section and
     update the link references.
  2. Set `.version = "X.Y.Z"` in `c/build.zig.zon` and `O11Y_VERSION` if
     applicable, and set `C_RELEASE_VERSION` in the `Makefile` and the
     default in `scripts/c-release-check.sh` to `vX.Y.Z`.
  3. Run `make c-check` and `make c-release-check` (or `make release-check`),
     then merge the release PR.
  4. Tag `c/vX.Y.Z` on the merge commit and push that tag.
  5. The release workflow (`scripts/release-tag.sh` routing `kind=c`,
     `module=libo11y-c`) checks `c/build.zig.zon` and `c/CHANGELOG.md`,
     runs `make c-check` and `scripts/c-release-check.sh`, and publishes the
     GitHub Release titled `libo11y-c vX.Y.Z` (never marked Latest, so Go
     keeps Latest) with the prebuilt archive and `SHA256SUMS`.
- The specification versions separately: once released, each version has a
  `spec/vX.Y.Z` tag and a schema file served at its schema URL. Spec
  1.0.0 is tagged `spec/v1.0.0` on the `go/v0.1.0` commit. Before
  tagging, `make schema-published` confirms the schema URL serves the
  generated file byte for byte. See [SPEC.md](SPEC.md), section 7.

## Naming

- The user-facing package/crate/artifact is named `o11y` where the ecosystem
  allows (Go package `o11y`, Rust crate `libo11y`, Java artifact `libo11y`).
- Metric and attribute names emitted on behalf of applications come from
  OpenTelemetry semantic conventions at the pinned version, with no vendor
  prefix. The library's own telemetry (the `o11y.schema.violations`
  metric, registered events, `o11y.config.*` startup attributes) uses the
  `o11y.*` namespace, which only the spec registry may mint.
- The semconv pin is recorded per language release and upgraded deliberately.
  Current pin: semconv v1.41.0.

## Environment variables

Standard `OTEL_*` variables are the only environment surface. libo11y defines
no `LIBO11Y_*` variables for anything OTEL specifies. If a knob has no OTEL
equivalent it is a code-level option, not an environment variable, until the
OTEL specification catches up.

## Commit messages

`<area>: <type>: <description>` all lowercase, where area is one of `go`,
`ts`, `spec`, `rust`, `java`, `zig`, `python`, `c`, `ruby`, `dotnet`, `docs`, `general`, and type follows
Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`,
`build`, `ci`, `perf`, `revert`) or names a Keep a Changelog category
(`change`, `removed`).

Example: `go: feat: add o11ytest recorder harness`

## Quality gates

`make ci` runs every gate locally, and `.github/workflows/ci.yml` runs the
same gates on pushes to `main` and on pull requests (Go 1.26.x, split into
parallel jobs). Every CI job calls the Makefile target except lint, which
runs golangci-lint v2.12.2 through `golangci/golangci-lint-action` on each
module. `make lint` runs whichever `golangci-lint` is on your `PATH`, so
install that version locally. Keep the two in step when adding a gate.

- Rust (planned): clippy pedantic, `unsafe_code = "forbid"`, cargo-deny.
