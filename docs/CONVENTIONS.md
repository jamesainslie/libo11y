# libo11y conventions

## Repository layout

```
libo11y/
  docs/          cross-language design contract, spec, and conventions
  spec/          telemetry specification registry: the shared,
                 language-neutral source of truth
  go/            Go module (github.com/jamesainslie/libo11y/go)
  rust/          Rust workspace (planned)
  java/          Java/Maven module (planned)
  zig/           Zig package (planned)
```

Each language directory is self-contained: its own build, tests, lint
configuration, changelog, and README. The `spec/` registry is the shared,
language-neutral source of truth; each language generates typed constants
and validation tables from it.

## Specification toolchain

The specification is validated and generated by the repository's own Go
tool (`go/internal/specgen`); the toolchain needs nothing beyond the Go
module itself. Make targets from the repository root:

- `make spec-check` decodes the registry strictly and validates it against
  the libo11y policy suite: naming, namespace ownership, sensitivity and
  cardinality classification, references and tombstones, enums, event
  discipline, and metric naming/unit rules. Rule IDs are listed in
  [SPEC.md](SPEC.md), section 8.
- `make spec-generate` validates first, then regenerates `go/spec`,
  `go/internal/spectables`, `docs/taxonomy`, and the OpenTelemetry schema
  file under `spec/schemas` from the registry. An invalid registry
  generates nothing. Generated files are never edited by hand.
- `make spec-drift` fails if generated artifacts are stale or if the
  generator produced files git does not track. CI runs it, and a golden
  test in `go test` catches the same drift.

The upstream semantic-conventions release the registry extends is pinned
as `semconv_version` in `spec/registry/manifest.yaml`; referenced upstream
attributes are defined by that release and never redefined here.

## Versioning and releases

- Independent per-language versioning, path-prefixed tags: `go/v0.1.0`,
  `rust/v0.1.0`.
- Semantic versioning per language ecosystem norms.
- No lockstep releases. A change to shared docs never forces a release.
- Each language keeps a `CHANGELOG.md` in Keep a Changelog format.
- Go releases tag `go/vX.Y.Z` first, then `go/o11ygin/vX.Y.Z`, whose
  `go.mod` requires the matching parent version. `make release-check`
  validates that sequence for the next unreleased version
  (`RELEASE_VERSION`, default `v0.1.0`) against a throwaway local remote;
  it never touches real refs. Bump the default after each release.
- The specification versions separately: once released, each version has a
  `spec/vX.Y.Z` tag and a schema file served at its schema URL. The 1.0.0
  schema file is served; the `spec/v1.0.0` tag does not exist yet. See
  [SPEC.md](SPEC.md), section 7.
- The repository is private: consumers set
  `GOPRIVATE=github.com/jamesainslie/libo11y` so the Go toolchain fetches
  it directly instead of through the public proxy and checksum database.

## Naming

- The user-facing package/crate/artifact is named `o11y` where the ecosystem
  allows (Go package `o11y`, Rust crate `libo11y`, Java artifact `libo11y`).
- Metric and attribute names emitted on behalf of applications come from
  OpenTelemetry semantic conventions at the pinned version, with no vendor
  prefix. The library's own telemetry (the `o11y.schema.violations`
  metric, registered events, `o11y.config.*` startup attributes) uses the
  `o11y.*` namespace, which only the spec registry may mint.
- The semconv pin is recorded per language release and upgraded deliberately.
  Current pin: semconv v1.41.0.

## Environment variables

Standard `OTEL_*` variables are the only environment surface. libo11y defines
no `LIBO11Y_*` variables for anything OTEL specifies. If a knob has no OTEL
equivalent it is a code-level option, not an environment variable, until the
OTEL specification catches up.

## Commit messages

`<area>: <type>: <description>` all lowercase, where area is one of `go`,
`spec`, `rust`, `java`, `zig`, `docs`, `general`, and type follows
Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`,
`build`, `ci`, `perf`, `revert`) or names a Keep a Changelog category
(`change`, `removed`).

Example: `go: feat: add o11ytest recorder harness`

## Quality gates

`make ci` runs every gate locally, and `.github/workflows/ci.yml` runs the
same gates on pushes to `main` and on pull requests (Go 1.26.x, split into
parallel jobs). Every CI job calls the Makefile target except lint, which
runs the same golangci-lint version (v2.12.2) through
`golangci/golangci-lint-action` on each module. Keep the two in step when
adding a gate.

| Target | Gate |
|---|---|
| `make lint` | golangci-lint v2 (with gofumpt) on both Go modules, zero issues; `golangci-lint fmt` applies the formatter |
| `make vet` | `go vet` on both modules |
| `make test` | `go test -race` on both modules (`GO_TEST_P` sets package parallelism), including the `testing/slogtest` handler contract, the OTLP wire tests, and the generator's golden test |
| `make tidy-check` | each module's `go.mod` and `go.sum` tidy on its own (`GOWORK=off`) |
| `make spec-check`, `make spec-drift` | registry policy checks and generated-artifact drift |
| `make release-check` | the Go release sequence (needs a clean tree) |
| `make vuln` | `govulncheck` on both modules; runs last because it depends on the advisory database and the toolchain's patch level |

- Go: the gates above. Standard-library advisories are fixed by the
  toolchain, not the module: build with go1.26.9 or later on the 1.26 line
  (or go1.27.2 or later on the 1.27 line), or `make vuln` reports them.
- Rust (planned): clippy pedantic, `unsafe_code = "forbid"`, cargo-deny.
- Java (planned): errorprone, spotless.
- Zig (planned): zig fmt, exhaustive switch on error sets.
